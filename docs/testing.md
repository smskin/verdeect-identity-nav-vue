# Тестирование продукта

Пакет проверяет себя сам; продукту остаётся проверить встраивание и вход.

## Что проверяет пакет

`npm test` в репозитории пакета — четыре проверки:

| Проверка | Что стережёт |
| --- | --- |
| полнота словаря | ключ без строки показался бы пользователю ключом |
| изоляция каталога | сеть, хранилища, чужие импорты, адреса, токены, пороги ширины |
| типы (`vue-tsc`) | самодостаточность пакета |
| правило текущего пункта | 16 наборов подсветки прямыми вызовами |

Повторять это в продукте не нужно.

## Вход в браузерных сценариях

```ts
import { loginAs, logout } from '@verdeect/identity-integration-vue/playwright';

await loginAs(page, 'user');
```

| Функция | Назначение |
| --- | --- |
| `loginAs(page, role, options?)` | проходит вход и возвращает управление на странице продукта |
| `logout(page)` | выход через блок пользователя — тем путём, которым пользуется человек |
| `credentialsFor(role)` | учётные данные из окружения |

Роль — `'admin'` либо `'user'`; учётные данные читаются из
`E2E_ADMIN_EMAIL`/`E2E_ADMIN_PASSWORD` и `E2E_USER_EMAIL`/`E2E_USER_PASSWORD`,
адрес установки — из `IDENTITY_BASE_URL`. Запасного адреса нет намеренно:
умолчание увело бы прогон на чужую установку молча.

### Селектор готовности — знание продукта

По умолчанию вход ждёт появления `.layout-wrapper` — оболочки Sakai, на которой
собраны продукты установки. Продукт с другой оболочкой передаёт свой селектор:

```ts
await loginAs(page, 'user', { readySelector: '#app-shell' });
```

Удобно завернуть это в тонкую обёртку продукта, чтобы сценарии не повторяли
селектор:

```ts
// tests/Browser/support/login.ts
import type { Page } from '@playwright/test';
import { loginAs as loginToInstallation, type Role }
    from '@verdeect/identity-integration-vue/playwright';

const READY_SELECTOR = '.layout-wrapper';

export async function loginAs(page: Page, role: Role): Promise<void> {
    await loginToInstallation(page, role, { readySelector: READY_SELECTOR });
}
```

### Вход идёт против настоящей установки

Против двойника поток входа не проверяется: PKCE, `state`, `nonce`, проверка
подписи и точное совпадение адреса возврата имеют смысл только при настоящем
сервере авторизации. Форма входа принадлежит установке — собственной формы
с паролем у продукта нет и быть не может.

Полезный приём: сторожевой сценарий, который проверяет доступность установки
и сам факт входа. При её отказе падает один сценарий, а не все истории разом.

## Что проверять в продукте

**Два представления смонтированы, ровно по одному каждое:**

```
substr_count($sources, 'placement="rail"') === 1
substr_count($sources, 'placement="overlay"') === 1
```

**Адрес открытой страницы передан в оба:**

```
substr_count($sources, ':current-url="currentUrl"') === 2
```

**Класс резервирования ставится по составу пунктов**, а не по факту входа.

**Правила порога стоят вне `@layer`** и повторяют числа навигации продукта.

Эти четыре условия — обязанности продукта, и проверяются по исходникам:
разметку собирает браузер, на сервере её нет. Поведение при разных ширинах
проверяет браузерный сценарий.

**Чего проверять не нужно:** сборку абсолютного адреса, выбор языка подписей,
правило подсветки, полноту словаря. Это обязанности пакета, и они покрыты
его прогоном.
