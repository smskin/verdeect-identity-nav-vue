# Правка эталона

Компоненты рейла и блока пользователя существуют в экосистеме **в одном
экземпляре** — в этом пакете. Продукты получают правку обновлением
зависимости.

## Почему копировать нельзя

Однажды уже разошлись. К моменту выделения библиотеки файлы жили в трёх местах:
в установке, во встроенном composer-пакете продукта и в самом продукте.
Компоненты совпадали, но их документация и стили разъехались попарно,
и сведение обошлось в отдельную работу по сверке каждого расхождения.

Правка «только у себя, потом перенесу» — тот же путь. Переносят не всегда.

## Правила каталога `src/cross-service`

Каталог обязан оставаться переносимым: внутри допустимы `vue` и собственные
файлы. Зависимости от шрифта иконок у каталога нет — иконки пунктов приходят
файлами, значки блока пользователя встроены. Проверяется
`npm run check:isolation`:

| Запрет | Причина |
| --- | --- |
| сетевые обращения (`fetch`, `XMLHttpRequest`, `WebSocket`…) | данные приходят только props |
| браузерные хранилища, `document.cookie` | кэш живёт на бэкенде продукта |
| импорты, кроме `vue` и локальных файлов | иначе каталог перестанет быть переносимым |
| адреса вида `http(s)://` | адреса приходят в данных |
| слово `token` | ключей доступа в браузере не бывает |
| числовые пороги ширины, `matchMedia`, `innerWidth` | порог принадлежит продукту |
| обращения к `document` вне двух разрешённых файлов | перечень закреплён константой с доводом |
| любые обращения к консоли | отладочная печать уехала бы в сборку каждого потребителя |
| `import.meta` | конструкция бандлера: вне его сборки роняет ветку, в которой стоит |

Девятым условием тот же скрипт проверяет, что ядро `src/identity` разбирается
**без** `@inertiajs/vue3`: знание про Inertia живёт только в адаптере.

Перечень разрешённых обращений к `document` правится вместе с доводом здесь же —
иначе он перестанет что-либо значить.

## Правила адаптера `src/public`

Вход `./public` — режим «Лендинг без бэкенда». **Ему одному в пакете разрешён
сетевой запрос**: у лендинга нет серверной части, и данные рейла некому
получить, кроме браузера. Остальные запреты каталога действуют и здесь:

| Запрет | Причина |
| --- | --- |
| импорты, кроме `vue`, `../identity`, `../cross-service` и локальных файлов | адаптер зависит только от ядра; Inertia и сетевые библиотеки не нужны |
| браузерные хранилища, `document.cookie` | ответ кэшируют установка и браузер по `Cache-Control` |
| обращения к консоли | журнала в пакете нет — причина отказа возвращается данными |
| `import.meta` | конструкция бандлера |
| адреса вида `http(s)://` | адрес установки приходит опцией |

Условием 12 проверяется обратное направление: ни `src/cross-service`, ни
`src/identity` адаптер не импортируют — ядро о нём не знает.

## Где лежат стили

Визуальный слой разбит по видам навигации, а `src/style.css` — оглавление
из `@import`:

| Файл | Что описывает |
| --- | --- |
| `styles/tokens.css` | переменные, включая `--cross-service-rail-width` |
| `styles/nav-shared.css` | блок `cross-service-nav` и его элементы: пункт, иконка, подпись, подсказка |
| `styles/nav-rail.css` | модификатор `--rail`: полоса, логотип, подсказка |
| `styles/nav-menu.css` | модификатор `--menu`: строки с подписями, заголовок, разделитель |
| `styles/nav-bar.css` | модификатор `--bar`: плашка внизу |
| `styles/user-menu.css` | блок пользователя |
| `styles/dark.css` | тёмная тема |

**Имя блока одно на три компонента.** `cross-service-nav` именует сущность
в разметке, а не файл: виды — его модификаторы. Поэтому общие правила пункта
и иконки живут в одном месте, а не тремя копиями.

**Порядок импортов в `style.css` значим.** Переменные нужны всем, общие правила —
видам, тёмная тема идёт последней: её правила той же избирательности, что
и обычные, и исход решает порядок. Перестановка строк — правка поведения.

Правило вида **уточняет** общее избирательностью
(`.cross-service-nav--rail .cross-service-nav__link` сильнее
`.cross-service-nav__link`), а не заменяет его: разделение по файлам каскад
не разделило. Перенося правило между файлами, проверяйте избирательность,
а не только место.

## Словарь подписей

Строки компонентов лежат в `src/cross-service/strings.ts`, а не в файлах
переводов продукта: продукт, встроивший рейл, словаря установки не ведёт.

Языки — `ru` и `en`: столько же, сколько у экранов входа установки, и `locale`
из `/userinfo` принимает одно из них. Неизвестный язык компонент отдаёт
запасным.

`npm run check:strings` проверяет: состав ключей совпадает между языками, оба
языка объявлены, все ключи, вызываемые компонентами, существуют. Формат словаря
обязан оставаться **плоским** — вложенность роняет разбор явной ошибкой.

## Прогон перед правкой и после

```bash
npm test
```

Словарь, изоляция, типы, правило подсветки. Прогон быстрый — гоняйте его
на каждое изменение каталога.

## Совместимость с бэкендом

Состав `NavItem` совпадает с ответом операций `GET|POST /api/navigation`
установки, а формы имени — с тем, что считает composer-пакет
`verdeect/identity-integration`. Границу держат две пары:

| В PHP | В TypeScript |
| --- | --- |
| `NavigationData.items` | `NavItem[]` |
| `UserProfile` | `IdentityProfile` |

Библиотеки лежат в разных репозиториях, и расхождение здесь пройдёт **молча**:
ни один прогон его не увидит. Поэтому изменение состава полей — согласованное
изменение обеих библиотек с согласованным minor, а не правка одной из них.

**Публичная операция установки.** Вход `./public` разбирает ответ
`GET /api/public/navigation` (PRD навигации 5.3, 5.8): `items` из
`{id, name, url, icon_url, order}` и `logo_url`; выключенная операция — `404`,
частота — `429`, любой параметр строки запроса — `400`. Разборщик пропускает
непригодный пункт и считает отказом только ответ без перечня — изменение
контракта операции правится здесь и в установке одновременно.

## Версии

Тег `vX.Y.Z` в репозитории; продукты подключаются по тегу. Правило —
одинаковый minor у обеих библиотек интеграции.

## Что менять нельзя без веской причины

- **Состав экспортов входа `.`** — продукты импортируют оттуда компоненты
  и типы.
- **Значения `data-placement`** (`rail`, `overlay`, `bottom`) — по ним
  таблицы стилей продуктов переключают виды.
- **Имя блока `cross-service-nav`** — оно общее у трёх видов, и на нём держатся
  общие правила оформления.
- **Имена `data-testid`** — на них опираются браузерные сценарии продуктов.
- **Имя переменной `--cross-service-rail-width`** — по ней продукты сдвигают
  оболочку.
