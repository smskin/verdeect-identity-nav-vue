## Задача одним абзацем

Две работы одним выпуском. Первая: установка научилась отдавать пункты
навигации неавторизованному посетителю, а `verdeect/identity-laravel` 0.4 —
их запрашивать; каталогу остаётся починить **язык**, который сегодня выводится
из профиля, которого у гостя нет. Вторая: рейл переходит на вид из макета
`.ai-factory/artifacts/Global Nav Bar.html` — полоса 64px с иконками без подписей, подсказка при
наведении, шестерёнка внизу, шторка и нижняя панель на телефоне.

## Макет даёт вид, контракт остаётся наш

**Контракт пропсов из макета не переносится** — он оторван от того, как пакет
получает данные, и от согласованного с `verdeect/identity-laravel` формата.
Каждое поле макета выражается тем, что у компонента уже есть:

| Макет | Чем выражается в пакете |
| --- | --- |
| `items: {id, label, icon, href}` | `NavItem: {id, name, url, iconUrl, order}` — `name` по языкам вместо одноязычного `label`, `iconUrl` вместо имени глифа |
| `activeId: string` | `currentItemId()` — двухъярусное правило по адресу открытой страницы, 16 наборов. Активный пункт вычисляется, а не диктуется |
| `authed: boolean` | Непустой `profileUrl` — договор задачи 4. Отдельный признак завёл бы второй источник истины о том же |
| `settingsHref: string` | Тот же `profileUrl` — адрес страницы профиля установки |
| `accent: string` | Переменные темы продукта (`--primary-color`, `--highlight-*`). Цвет в пропсах уехал бы в продукт с другой темой чужим |
| `sections: {id, label, href}[]` | Не переносится: разделы принадлежат продукту, установка о них не знает. В шторке они рисуются продуктом **после** блока пакета — шов уже есть, это `cross-service-nav__divider` |
| `onSelect(id)` | Не переносится: пункты — обычные ссылки `<a href>`. Закрытие шторки по выбору делает продукт, который её и открыл |

## Что из макета не переносится и почему

- **Порог 1024px** — в пакете запрещён и остаётся запрещённым:
  `check-component-isolation.mjs` условие 8 роняет `npm test` на строках
  `1024`, `matchMedia`, `innerWidth`. Порог обязан совпадать с порогом
  навигации продукта, поэтому живёт в его таблице стилей. Число из макета
  идёт в документацию как рекомендуемое, а не в код.
- **Перекраска активной иконки в акцент** (`иконка accent`) — невыполнима:
  иконка приходит файлом по `iconUrl`, изображение цвет не наследует, а маска
  по силуэту превратила бы многоцветный файл в силуэт (решение PRD 9.4,
  коммит `79cdec3`). Активность выражается **только заливкой плашки** —
  единственное расхождение с макетом по состояниям, и оно осознанное.
- **Литеральные цвета макета** (`#f4f4f4`, `#e9e4fb`, `#8265EA`) — идут
  **запасными значениями** переменных темы, а не вместо них. Зашитые
  literalами, они перестали бы следовать теме продукта.
- **Бургер и всплывающее меню нижней панели** — состояние принадлежит
  продукту: это его меню, как и шторка сегодня. Пакет даёт представление
  `bottom`, продукт решает, добавлять ли к нему бургер.

- [x] **3. Порядок разрешения языка**
  **Файл:** `src/identity/useIdentityView.ts`
  Сейчас `locale` — это `profile.value?.locale ?? 'ru'` (строка 54). Заменить
  порядком: язык профиля → `locale` свойств продукта → `'ru'`.
  Профиль остаётся первым: у вошедшего язык принадлежит ему, а не странице,
  и смена языка в профиле обязана доходить до рейла.

  только добывает свойства страницы и её адрес: новое необязательное поле

  недоступно продукту на другой схеме доставки.
  **Что правка не чинит.** Вошедшего с пустым утверждением `locale`: парная
  библиотека подставляет жёсткий `'ru'` вместо пустого значения

  подставленный язык от осознанно выбранного на стороне пакета нечем — профиль
  непуст, и порядок разрешения до свойств продукта не доходит. На англоязычной
  установке такой пользователь получит русский рейл. Исправление — сквозная
  передача пустого значения из PHP-пакета, и это предмет отдельной
  согласованной правки, а не этого выпуска.
  **Логирование:** нет.
