# cross-service — Переносимые компоненты кросс-сервисной навигации

## Overview

**Purpose**: Рейл переходов между сервисами установки и блок пользователя единого входа (PRD навигации 7.1–7.4, 9.1–9.3).

**Location**: `src/cross-service/` пакета `@verdeect/identity-nav-vue`.

**Pattern**: Каталог **вынут** в отдельный репозиторий и отдаётся npm-пакетом — входом `.`. Выемка была перемещением каталога, а не переписыванием: поэтому данные приходят только свойствами, а словарь строк живёт внутри каталога. Копий в продуктах не осталось ни одной: правка идёт сюда, продукты получают её обновлением зависимости.

Каталог живёт по своим правилам, и они строже общих: разделы ALWAYS и NEVER ниже — часть контракта, а не пожелание.

## File Catalog

### types.ts

**Purpose**: Типы свойств обоих компонентов.

**Exports**: `NavItem`, `ProductMenuItem`, `NavPlacement`, `CrossServiceRailProps`, `CrossServiceMenuProps`, `CrossServiceBarProps`, `UserMenuProps`. `NavPlacement` — не проп, а перечень значений атрибута `data-placement`: вид задаётся выбранным компонентом.

**Key behaviour**: состав `NavItem` совпадает с ответом операции `POST /api/users/services` (PRD навигации 5.3) — продукт передаёт `items` ответа как есть. Индексных сигнатур нет: они заглушили бы обращение к несуществующему полю.

### strings.ts

**Purpose**: Словарь строк по языкам и функция `translate(locale, key)`.

**Key behaviour**:

- **Осознанное отступление от правила «отображаемого текста в коде нет»**, предписанное PRD 9.1: продукт словаря сервиса не ведёт, а словарь переехал в пакет вместе с компонентом.
- Неизвестный язык — строка первого объявленного языка, молча. Язык гостя определяет продукт по `Accept-Language`, поэтому чужое значение штатно, а не ошибка встраивания; предупреждать не о чем.
- Неизвестный ключ возвращается сам собой.
- Формат словаря **обязан оставаться плоским**: проверка читает файл текстом.

### currentItem.ts

**Purpose**: Правило текущего пункта (PRD навигации 7.3).

**Exports**: `currentItemId(items, currentUrl): string | null`.

**Key behaviour**: правило двухъярусное, и схема с хостом обязательны на обоих ярусах (порт — часть хоста).

- **По пути.** Пути сравниваются без завершающего `/` и посегментно, поэтому `/user` не подсвечивается на `/users`; пустой путь пункта совпадает с любой страницей хоста; при нескольких совпадениях побеждает самый длинный путь, при равной длине — первый по порядку.
- **По хосту, запасной.** Не совпал никто — текущим становится первый по порядку пункт того же хоста. Пока человек на домене сервиса, рейл показывает, где он: раздел, на который пункта нет, — случай обычный, и погашенная подсветка сообщала бы, что человек ушёл с сервиса.

Отсюда: единственная ссылка на домен горит всюду на нём; при нескольких точное совпадение пути побеждает запасное. Строка запроса и якорь не участвуют. Непригодный адрес — пропуск пункта, а не отказ, и запасным ответом он тоже не становится.

Непригодный адрес страницы — `null` на всё правило разом: сравнивать не с чем, и полоса не подсвечивает ничего. Относительный путь непригоден именно поэтому — схемы и хоста в нём нет.

### CrossServiceRail.vue / CrossServiceMenu.vue / CrossServiceBar.vue

**Purpose**: три вида одного содержимого. `CrossServiceRail` — постоянная полоса слева (десктоп); `CrossServiceMenu` — блок внутри выдвижного меню продукта (мобильный вид 1); `CrossServiceBar` — плашка внизу экрана (мобильный вид 2).

**Продукт монтирует два из трёх**: полосу и **один** мобильный вид. Мобильные виды взаимоисключающие — вместе они покажут одни и те же пункты дважды. Плашка внизу подходит не всякой оболочке, поэтому выбор оставлен продукту.

**Props**: общие — `items`, `locale`, `currentUrl?`, `profileUrl?`; `logoUrl` **только** у `CrossServiceRail` (логотип рисует одна полоса).

**Test hooks**: `cross-service-nav`, `cross-service-logo`, `cross-service-item-<id>`, `cross-service-item-current`, `cross-service-settings`; у плашки внизу — ещё `cross-service-more`, `cross-service-popup`, `cross-service-popup-item-<id>`, `cross-service-scrim`.

**Key behaviour**:

- **Пропа `placement` нет: вид — это выбранный компонент.** Прежний общий компонент требовал `logoUrl` у всех трёх, показывая логотип в одном, и не мешал смонтировать полосу внутрь выдвижного меню. Каждый вид сам проставляет `data-placement` (`rail`, `overlay`, `bottom`) — по нему переключает таблица стилей продукта.
- **Шестерёнка настроек рисуется при непустом `profileUrl`.** Признак входа выражен адресом, а не отдельным полем: гостю установка адреса профиля не отдаёт. Отдельный `authed` был бы вторым источником истины о том же.
- **Подписи есть только в `CrossServiceMenu`.** В полосе имя показывает подсказка при наведении (чистый CSS, без состояния и обращений к DOM); в плашке подсказки нет — на телефоне наведения не существует. Имя всюду доступно через `aria-label`.
- **Общие правила живут в `useNavView.ts`**, иконка — в `NavIcon.vue`, шестерёнка — в `SettingsLink.vue`, подсказка — в `NavTip.vue`. Скопированные в три вида, они разошлись бы первыми.
- **Подсказка полосы уезжает в `body` через `Teleport`, и иначе нельзя.** Полоса обязана прокручиваться при переполнении (PRD навигации 7.2) — это `overflow-y: auto`, а по спецификации CSS вторая ось тогда вычисляется из `visible` в `auto`. Подсказка по построению выходит за правый край полосы и обрезалась там до одного уголка. Оформительского решения у задачи нет: внутри прокручиваемого предка обрежет любой из них. Координаты `NavTip` снимает с самой ссылки и пересчитывает на прокрутке — слушателем **на этапе перехвата**, потому что событие вложенной полосы до окна не всплывает.
- **Состав плашки внизу решает измерение, а не число.** Пока пункты помещаются в строку, стоят все, а шестерёнка занимает последний слот; не помещаются — последний слот занимает контрол `cross-service-more`, раскрывающий список **всех** пунктов, и шестерёнка уходит в него последней строкой за швом. Сколько кнопок помещается, `CrossServiceBar` меряет по настоящей отрисованной кнопке и промежутку строки, наблюдая за шириной через `ResizeObserver`: ширины экрана продукта и его отступов пакет не знает, и любой порог, записанный числом, разошёлся бы с оболочкой (см. докблок `index.ts`).
- **Прокрутки вбок у плашки больше нет, и это осознанная замена.** Пункт за правым краем оставался достижимым, но невидимым: полосы прокрутки на телефоне не видно, а о прокрутке в строке из четырёх кнопок никто не догадывается. Всплывающий список показывает то же самое разом и подписями — правило «ни один пункт не исчезает» исполнено, а не отменено.
- **Логотип — плитка во всю ширину полосы, прижатая к верхнему краю** (макет, кадр «Desktop rail»), а не значок в ряду пунктов: без скругления, отрицательным верхним отступом гасит `padding` полосы. Отступ вынесен в `--cross-service-rail-padding` — два числа, здесь и там, разошлись бы, и плитка отъехала бы от края незаметно.
- **`currentUrl` необязателен только для страниц с полной перезагрузкой.** Умолчание — адрес окна, вычисленный **один раз при монтировании**. Приложению с сохраняемой оболочкой (Inertia, любой SPA) этого мало: переход между разделами оболочку не перемонтирует, и подсветка застревает на первой открытой странице. Такой продукт передаёт адрес сам — и **абсолютным**, см. «Адрес открытой страницы».
- Пустой `items` не даёт ничего — ни пунктов, ни логотипа, ни заголовка.
- Логотип показывается **по факту загрузки**; места под него не резервируется, ошибка загрузки пустого места не оставляет.
- Не загрузившаяся иконка заменяется первой буквой имени (PRD 9.4). Признак — событие `error` изображения либо пустой `iconUrl`; последнее означает установку, ещё не перешедшую на загружаемые иконки. Обращения к отрисованному узлу ради этого больше нет: прежде компонент читал псевдоэлемент `::before`, выясняя, нарисован ли глиф.
- Переход — обычная ссылка в той же вкладке; перехвата нажатия нет.

### UserMenu.vue

**Purpose**: Блок пользователя единого входа (PRD навигации 9.3).

**Props**: `shortName`, `name`, `initials`, `email?`, `profileUrl`, `locale`, `items?`. Событие — `logout`.

**Test hooks**: `user-menu`, `user-menu-trigger`, `user-menu-name`, `user-menu-email`, `user-menu-profile`, `user-menu-logout`, `user-menu-item-<индекс>`.

**Key behaviour**:

- Формы имени приходят готовыми; инициалы не вычисляются.
- Порядок меню задан PRD и не настраивается: шапка, «Профиль», пункты продукта, «Выход».
- Без `email` строки адреса нет.
- «Выход» порождает событие и **никуда не перенаправляет**.
- Закрывается по `Esc`, нажатию вне и переходу по пункту; слушатели живут только пока меню раскрыто.

### index.ts

**Purpose**: Точка входа каталога и вход `.` пакета, поэтому продукт ввозит отсюда, а не из отдельных файлов: раскладка файлов внутри каталога на его импорты не влияет.

## ALWAYS

- **Данные приходят только свойствами.** Ответ операции 5.3 передаётся как есть.
- **Словарь строк — внутри каталога**, состав ключей одинаков у всех языков, перечень языков совпадает с языками установки.
- **Порядок пунктов — как передан.** Он задан реестром; сортировка «на всякий случай» разошлась бы с сервером при равных значениях `order`.
- **Логотип показывается по загрузке**, места заранее не занимает.
- **Опорные точки проверок — `data-testid`.** Подписи различаются языком.

## NEVER

- **Не выполнять сетевых запросов** — ни `fetch`, ни `XMLHttpRequest`, ни переходов Inertia.
- **Не обращаться к браузерным хранилищам** — ни `localStorage`, ни `sessionStorage`, ни `indexedDB`, ни `document.cookie`. Кэш живёт на бэкенде продукта.
- **Не импортировать код приложения и PrimeVue.** Допустимы `vue` и файлы каталога. Компонент PrimeVue потянул бы за собой библиотеку, которой у продукта может не быть. Шрифт иконок — тем же доводом: классы `pi pi-*` здесь больше не применяются.
- **Не вычислять инициалы и формы имени** — они приходят готовыми.
- **Не выполнять выход и не перенаправлять** — компонент порождает событие.
- **Не вести перечень иконок** — рассинхрон версий штатен.
- **Не пересортировывать пункты.**
- **Не писать в консоль вовсе** и **не трогать `import.meta`.** Второе — конструкция бандлера: вне его сборки обращение к ней роняет ветку, в которой стоит. Оба запрета проверяются условиями 6 и 6a `check:isolation`.
- **Не задавать порога узкого экрана** — ни числом, ни константой, ни медиазапросом, ни наблюдением за шириной.

Соблюдение проверяется `scripts/check-component-isolation.mjs` и `scripts/check-component-strings.mjs` — обе исполняются `npm test`.

### Порог узкого экрана — обязанность продукта

Компонент проставляет на корневом элементе `data-placement` (`rail` либо `overlay`) и метит краткую форму имени классом `cross-service-user__short-name`. **Когда показывать каждое из представлений, решает продукт** — тремя правилами своей таблицы стилей, со **своим** порогом: тем же, на котором переключается его собственная навигация. PRD 7.1 называет узкий экран «единственным случаем, когда рейл зависит от навигации продукта: собственного мобильного режима у него нет».

В `identity-service` правила стоят в его `resources/css/app.css` рядом с порогом оболочки Sakai. **Числа тамошние, а не пакета:**

```css
@media (min-width: 992px) {
    [data-placement='overlay'] {
        display: none;
    }
}

@media (max-width: 991px) {
    [data-placement='rail'] {
        display: none;
    }

    .cross-service-user__short-name {
        display: none;
    }
}
```

Продукт с порогом 768 пишет те же три правила со своим числом. Порог, зашитый в пакет, уехал бы в продукт чужим.

### Место под рейл — обязанность продукта

Рейл занимает **всю высоту окна** и лежит самым внешним слоем (макет 2a):
`position: fixed; top: 0; left: 0`. Высоты чужой шапки он не знает и знать
не должен — это то же знание о хозяине, что и порог узкого экрана.

Отсюда обязанность продукта: **подвинуть собственную оболочку вправо** на ширину
рейла — шапку, навигацию **и содержимое**. Ширина объявлена переменной
`--cross-service-rail-width` (`src/style.css`, вход `./style.css`), поэтому число
не повторяется. Правил пять, и все пять обязательны — вот они целиком, как стоят
в `identity-service` (его `resources/css/app.css`):

```css
@media (min-width: 992px) {
    .layout-wrapper.layout-has-rail .layout-topbar {
        left: var(--cross-service-rail-width);
        width: calc(100% - var(--cross-service-rail-width));
    }

    .layout-wrapper.layout-has-rail.layout-static:not(.layout-static-inactive)
        .layout-sidebar {
        left: calc(2rem + var(--cross-service-rail-width));
    }

    .layout-wrapper.layout-has-rail.layout-static .layout-main-container {
        margin-left: calc(22rem + var(--cross-service-rail-width));
    }

    .layout-wrapper.layout-has-rail.layout-static.layout-static-inactive
        .layout-main-container,
    .layout-wrapper.layout-has-rail.layout-overlay .layout-main-container {
        margin-left: 0;
        padding-left: calc(2rem + var(--cross-service-rail-width));
    }
}
```

Числа `2rem` и `22rem` — величины самой оболочки Sakai, поэтому здесь они уместны
долями; пиксели рейла прибавляются переменной.

Что даёт каждое:

- **Шапка.** Оставленная во всю ширину, она накрыла бы рейл сверху, и гамбургер
  продукта повис бы над чужой полосой.
- **Сайдбар.** Сужение до `:not(.layout-static-inactive)` обязательно: свёрнутую
  навигацию Sakai уводит за край через `translateX(-100%)` при `left: 0`,
  и безусловный `left` вернул бы её краем в кадр поверх рейла.
- **Содержимое, навигация развёрнута.** Sakai отводит ему `margin-left: 22rem`;
  сдвинув сайдбар и забыв содержимое, продукт получает наезд рейла на текст —
  у заголовка срезает левый край.
- **Содержимое, навигация свёрнута или в оверлее.** Отступа под сайдбар здесь нет,
  и место освобождается `padding-left` вместо `margin-left`.

Пропуск двух правил для `.layout-main-container` — то, что случилось в первом же
продукте, забравшем каталог по этой справке, когда она приводила одно правило
из пяти.

### Адрес открытой страницы — обязанность продукта

Правило текущего пункта сравнивает схему и хост, а значит начинает с разбора
адреса. Относительный путь не разбирается: `new URL('/directory')` бросает
исключение, `currentItemId` ловит его и возвращает `null`. Полоса гаснет
целиком — молча, без ошибки в консоли и без записи в журнале.

Inertia отдаёт в `page.url` именно путь. Переданный как есть, он не подсвечивает
ничего и никогда:

```ts
// неверно: путь, а не адрес — подсветки не будет ни на одной странице
currentUrl: page.url,

// верно
currentUrl: `${window.location.origin}${page.url}`,
```

**Умолчание компонента здесь не выручает.** Оно вычисляется один раз при
монтировании, а переход Inertia оболочку не перемонтирует: подсветка застряла бы
на первой открытой странице. Продукту с сохраняемой оболочкой передавать
`currentUrl` обязательно.

Сборка переехала в пакет и продукту писать её незачем: вход `./identity`
(`src/identity/useIdentityView.ts`) собирает адрес сам, а продукту на Inertia
хватает входа `./inertia` (`src/inertia/useIdentity.ts`). Место удачное: данные
страницы достаются один раз, и оба представления рейла — полоса и оверлей —
получают один и тот же адрес. Продукт, собирающий адрес сам да ещё в разных
компонентах, рискует собрать его дважды и по-разному.

Признак ошибки на глазок: полоса не подсвечивает **ни одного** пункта ни на одной
странице продукта, включая его корень. Дефект реестра или правила выглядел бы
иначе — подсветка пропадала бы выборочно.

### Политика `img-src` продукта

Логотип установки раздаётся сервисом по постоянному адресу и приходит свойством `logoUrl`. **Политика безопасности содержимого продукта обязана включать origin сервиса в `img-src`** (PRD 9.1) — иначе рейл покажет пустое место вместо логотипа, а причина будет видна только в консоли обозревателя, потому что компонент об ошибке не сообщает и места под логотип не резервирует.

- `vue`;
- `src/style.css` — оформление, живущее в пакете рядом с каталогом (вход `./style.css`).

Шрифта иконок среди зависимостей **нет**: иконки пунктов рисуются изображениями
по `NavItem.iconUrl`, значки блока пользователя встроены в `UserMenu.vue`
как SVG. Возвращать `pi pi-*` не следует — их подключение было обязанностью
каждого продукта установки, а продукты о шрифте не знают.

Импортов из приложения нет и быть не должно.

## Testing

- **Чистота исходников** — `npm run check:isolation` (`scripts/check-component-isolation.mjs`): сеть, хранилища, импорты, адреса, токены, консоль, `document`, пороги ширины, а девятым условием — что ядро `src/identity` разбирается без Inertia.
- **Полнота словаря** — `npm run check:strings` (`scripts/check-component-strings.mjs`).
- **Правило текущего пункта** — `tests/currentItem.spec.ts`: шестнадцать случаев прямыми вызовами, браузер не поднимается.
- **Типы** — `npm run types:check` (`vue-tsc --noEmit`).
- **Поведение в интерфейсе** — браузерные сценарии продуктов установки: они проверяют встраивание, а не правила самих компонентов.

Всё разом — `npm test`.
