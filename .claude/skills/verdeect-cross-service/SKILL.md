# Контракт пакета @verdeect/identity-nav-vue

Пакет отдаёт продуктам установки рейл кросс-сервисной навигации, блок
пользователя единого входа, их визуальный слой, вывод состояния рейла и вход
в продукт для браузерных прогонов. Правила ниже — часть контракта, а не
пожелание: их нарушение либо ломает потребителя, либо расходится с эталоном
молча.

## 0. Три вещи, которые ломают пакет чаще всего

1. **Числовой порог ширины внутри пакета.** Порог принадлежит продукту
   (см. §3). Константа «чтобы не забыть значение» уедет в продукт с другим
   порогом чужой.
2. **Импорт в `src/cross-service` чего угодно, кроме `vue` и файлов
   каталога.** Каталог — эталон экосистемы; лишний импорт делает его
   непереносимым.
3. **Шаг сборки.** Пакет поставляется исходниками (§2). Сборщик, бандлер,
   Tailwind, storybook сюда не заводятся ни под каким предлогом.

## 1. Эталон и его правка

Каталог `src/cross-service` перенесён из `verdeect-identity-service`
(коммит `c3b7f14`) и является **единственным источником истины** для всей
экосистемы: копий в продуктах не осталось ни одной. Правка идёт сюда, продукты
получают её обновлением зависимости.

**Отсюда правило правки:** файлы каталога меняются только по существу. Они
сверяются с эталоном глазами, поэтому переименование переменной «для красоты»,
переформатирование и косметика в докблоках создают шум, который придётся
разбирать вручную.

Полные правила каталога и их проверка — [references/ISOLATION.md](references/ISOLATION.md).

## 2. Библиотека, а не приложение

Пакет поставляется исходниками — `.vue`, `.ts` и `.css` **без шага сборки**:
интерфейс собирает Vite потребителя, а `@vitejs/plugin-vue` обрабатывает `.vue`
в зависимостях наравне со своими.

**Собственной зависимости от Vite у пакета нет.** Её не должно быть и в коде:
`import.meta.env` — конструкция бандлера, и вне его сборки (отрисовка
на сервере, другой бандлер у потребителя) обращение к ней роняет ветку,
в которой стоит. Запрет держит условие 6a `check:isolation`.

**Не предлагать и не заводить:** `vite build`, rollup, бандл библиотеки,
storybook, Tailwind, PostCSS-конвейер, а также всё, что относится к приложениям
(Laravel, PHP-скиллы, серверная часть, база данных, ORM).

## 3. Пороги ширины принадлежат продукту

Числовых порогов в пакете **нет ни одного**, и заводить их нельзя — ни числом,
ни константой, ни медиазапросом, ни наблюдением за шириной
(`matchMedia`, `innerWidth`, `ResizeObserver`).

Каждый вид навигации проставляет на корневом элементе `data-placement`
(`rail`, `overlay` либо `bottom`) и метит краткую форму имени классом
`cross-service-user__short-name`. Какой вид показать — решает таблица стилей
продукта своим медиазапросом, тем же, на котором переключается его собственная
навигация: собственного мобильного режима у рейла нет.

## 4. Шесть входов и их границы

| Вход | Файлы | Что допустимо |
| --- | --- | --- |
| `.` | `src/cross-service/` | `vue` и файлы каталога, и ничего больше |
| `./style.css` | `src/style.css`, `src/styles/*.css` | переменные темы продукта; порогов нет |
| `./identity` | `src/identity/` | `vue`; правила вывода состояния |
| `./inertia` | `src/inertia/` | `vue` + `@inertiajs/vue3`; только адаптер |
| `./public` | `src/public/` | `vue`; адаптер лендинга без бэкенда, единственный сетевой запрос пакета |
| `./playwright` | `src/playwright/` | `@playwright/test`; окружение прогона |

Ядро `./identity` отделено от адаптера `./inertia` намеренно: правила вывода
принадлежат библиотеке, знание о схеме доставки данных — нет. Появившееся
в адаптере правило было бы недоступно продукту на другой схеме.

Границы входов, разрешённые зависимости и порядок заведения нового входа —
[references/ENTRIES.md](references/ENTRIES.md).

## 5. Обязанности продукта не переезжают в пакет

Пакет намеренно не знает о хозяине. Обязанности встраивающего продукта
(два вида навигации из трёх, правила переключения вне `@layer`, сдвиг оболочки,
абсолютный `currentUrl`, `locale` для гостя, `img-src`, переменные темы)
перечислены в `docs/checklist.md` и **остаются продукту**. Обязанности лендинга
без бэкенда (включённая публичная операция в установке, `connect-src`,
`path` из маршрутизатора) — в `docs/landing.md`. Соблазн «сделать за продукт»
внутри пакета — та же ошибка, что зашитый порог.

Внешний контракт, парная composer-библиотека и порядок выпуска —
[references/CONTRACT.md](references/CONTRACT.md).

## 6. Стиль кода

- TypeScript `strict`, `<script setup lang="ts">`, без `any`.
- Четыре пробела, одинарные кавычки, точка с запятой, висячая запятая.
- Возвращаемый тип функции указывается явно, включая `void`.
- Сторожевые условия и ранние `return`; сравнение с `null` строгое и явное.
- Экспорты именованные; `export default` — только для SFC через `index.ts`.
- Свойства — `defineProps<Props>()` с типом из `types.ts`, умолчания —
  `withDefaults`; события — `defineEmits<{ … }>()`.
- **Комментарии и докблоки по-русски и объясняют ПРИЧИНУ**, а не пересказывают
  код. Докблок файла отвечает «почему этот файл существует и устроен так»;
  докблок правила — «что случится, если сделать иначе». Этот стиль выдержан
  во всём пакете, включая перенесённый эталон.
- Расширение закреплённых перечней (файлы с доступом к `document`, допустимые
  обращения к консоли) сопровождается доводом рядом с перечнем: без довода
  перечень перестаёт что-либо значить.

Полные соглашения — `.ai-factory/rules/base.md`.

## 7. Прогон

```bash
npm test
```

Четыре проверки подряд:

1. `check:strings` — полнота словаря подписей;
2. `check:isolation` — изоляция каталога и «ядро разбирается без Inertia»;
3. `types:check` — `vue-tsc --noEmit`;
4. `test:unit` — правила прямыми вызовами (26 наборов): подсветка текущего
   пункта, разрешение языка, выбор подписей.

**Разметку наборы не проверяют** — прогонщик не разбирает `.vue`, а второй
прогонщик заводить нельзя (см. ниже). Что рисуют компоненты, проверяют
браузерные сценарии продуктов.

Браузер не поднимается ни одним набором: `@playwright/test` служит прогонщиком
Node. **Отдельного прогонщика не заводить** — Playwright уже нужен входу
`./playwright`. Vitest, Jest и прочие сюда не добавляются.

Проверки идут через `&&`, поэтому падение первой скрывает остальные: разбирать
надо по одной, а перед сдачей работы прогонять `npm test` целиком.

## 8. Порядок правки

1. Понять, какому входу принадлежит изменение (§4). Правка не своего входа —
   почти всегда признак того, что решение принято не на том уровне.
2. Внести изменение по существу, без косметики в соседних строках.
3. Докблок — если появилось правило, чьё нарушение неочевидно.
4. Прогнать `npm test` целиком.
5. Изменение контракта данных (`NavItem`, `IdentityProfile`,
   `CrossServiceData`) согласовать с `verdeect/identity-laravel`
   и выпустить согласованным minor — см. [references/CONTRACT.md](references/CONTRACT.md).

## 9. Совместное применение с `vue-best-practices`

Внешний навык `vue-best-practices` даёт общие правила Vue 3 и применим к стилю
SFC, реактивности и типизации props/emits.

**При расхождении побеждает контракт пакета.** Неприменимо к этой библиотеке:
- дробление компонентов на подкомпоненты и «feature folder» —
  Виды навигации и `UserMenu` переносимы целиком, их раскладка закреплена;
- Pinia, Vue Router, provide/inject — данные приходят только props;
- вынос логики в композаблы внутри `src/cross-service` — каталог держит ровно
  тот состав файлов, который переезжает;
- любые советы про адаптивность через наблюдение за шириной — см. §3.
